# ADR 0011 — The examiner console (web frontend)

**Status:** accepted
**Scope:** `web/`

## What was built

A React 19 + TypeScript single-page app, built with Vite, that drives
`pramaan.api` end to end: case creation and listing, evidence and clip
intake, the composed multi-channel timeline (rendered as a real SVG
chart, not a table pretending to be one), examiner findings, audit-
ledger integrity verification, and generating all three of Pramaan's
downstream documents -- the Section 63(4) certificate, the narrative
case report, and a SEF export bundle -- each returned by the API as
bytes and saved directly to the examiner's disk. Every page is wired to
a real, running API; there is no mock data anywhere in the app.

## Design decision: TanStack Query owns every piece of server state

Hand-rolled `useEffect` + `useState` data fetching was rejected up front
for anything beyond the most trivial page: it means re-deriving loading
state, error state, and race-condition handling (a fast second request
resolving before a slow first one) in every component that fetches
anything, with no shared correctness guarantee between them. TanStack
Query centralizes that once, and a query-key registry
(`src/hooks/queries.ts`) is the single place a mutation's
`invalidateQueries` call and a query's own key are defined, so the two
can't drift apart by one component hand-typing an array key elsewhere.

## Design decision: a single light theme, not a light/dark toggle

Every color, font, and surface token lives in one `@theme` block in
`src/index.css`; components reach for the generated Tailwind utilities
(`bg-surface-1`, `text-text-secondary`, `border-line`, the `kind-*`
tokens for clip/segment coloring) rather than raw hex values anywhere in
a component file. A toggle was considered and deliberately deferred: a
second theme nobody has actually looked at across every page is a
liability, not a feature -- one theme, fully built, checked page by page
in a real browser, was judged more valuable than two half-verified ones.

## Design decision: reports and exports are downloaded, never left on the server

`pramaan.api`'s report and export endpoints return the file's bytes
directly rather than a path (see [ADR 0010](0010-api-layer.md)); the
frontend mirrors that by using `URL.createObjectURL` on the response
`Blob` and triggering a throwaway anchor-click download
(`src/lib/download.ts`), reading the suggested filename from the
response's own `Content-Disposition` header rather than guessing one.
Nothing generated by a report or export request is retained anywhere in
the browser after the download completes.

## Design decision: hand-written API types, not a generated client

`src/api/types.ts` mirrors `pramaan/api/schemas.py` field-for-field by
hand rather than through an OpenAPI code generator. For a schema this
size, generation would trade a few hundred lines of hand-written types
for a build-time dependency on the API being reachable (or its schema
committed and kept in sync some other way) -- a real cost for a project
that otherwise has zero code-generation steps. The tradeoff is honest:
the two files can drift, and the fix if they ever do is the same as any
hand-synchronized pair in this codebase -- update both, and let the
first broken request or failing test say so.

## A real bug caught before manual testing: `className` silently discarded base input styling

`TextField`, `TextAreaField`, and `SelectField` originally hard-coded
`className={CONTROL_CLASS}` on their underlying element and spread
`{...rest}` afterward -- so the moment any caller passed its own
`className` (as the SHA-256 fields do, to add monospace styling), the
spread's `className` silently replaced `CONTROL_CLASS` entirely rather
than extending it, stripping every border, padding, and focus-ring style
from that one field. Fixed by destructuring `className` explicitly and
merging it (`` `${CONTROL_CLASS} ${className}` ``) instead of letting a
later spread win outright. Caught by inspection while wiring the first
field that actually passed a `className`, before it reached a browser.

## A real bug caught in manual browser verification: wrong prop type on the button components

`PrimaryButton` and `SecondaryButton` were typed with
`InputHTMLAttributes<HTMLButtonElement>` -- attributes for an `<input>`
element, applied to a `<button>`. TypeScript caught this immediately at
build time (`type="submit"` isn't assignable to `InputHTMLAttributes`'s
narrower `type` union), not silently: `npm run build` failed outright
until it was fixed to the correct `ButtonHTMLAttributes<HTMLButtonElement>`.
Worth recording because it demonstrates exactly what strict TypeScript
is for here -- this class of mismatch is caught by the type checker
before a single browser loads the page, not discovered by a user
clicking a broken submit button.

## Verified end to end in a real browser, not just by the test suite

Beyond the Vitest suite, the complete workflow was driven manually
against a live `pramaan.api` instance: create a case, add an evidence
item (confirming the SHA-256 field renders in monospace and the size
formats as "100.0 MB"), add a clip with a start/end time, and confirm
the Timeline tab renders a real SVG bar for that clip on its correct
channel with the correct kind color and correctly formatted axis labels
-- not a screenshot of intended behavior, an actual rendered page
checked against an actual running backend, with the browser console
confirmed clear of errors throughout.

## Verification run before this was committed

- `npm run build` (`tsc -b && vite build`): clean, zero type errors.
- `npm run lint` (oxlint): clean.
- `npm run test` (Vitest + React Testing Library): 24/24 passing, covering
  the formatting helpers, the API client's error normalization and file-
  download filename extraction, the timeline chart's rendering logic, and
  the new-case form's full submit/error interaction.
- Manual end-to-end verification in a real browser against a live
  `pramaan.api` instance, as described above.

## Consequences

This is the last layer in the originally planned stack: acquisition,
filesystem interpretation, recovery, integrity, timeline, case
management, export, both report documents, the API, and now the
examiner-facing UI are all implemented, tested, and wired together end
to end. Further UI work from here is refinement (acquisition/recovery
triggered from the UI rather than only recorded after the fact, signed
SEF export once a key-management endpoint exists) rather than a new
layer.
